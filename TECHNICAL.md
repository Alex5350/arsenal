# TECHNICAL.md

For the engineer inheriting this repository. The why of the design lives in
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) as short decision records; this
file is the operating manual: layout, contracts, and how to extend.

## Layout

```
AGENTS.md                     universal entry every harness reads
CLAUDE.md                     Claude Code adapter (@imports docs/)
.github/copilot-instructions.md   Copilot adapter
opencode.json                 OpenCode config: tier agents, role-agent pointers
.agents/skills/<name>/SKILL.md   canonical skills (edit here)
.claude/agents/<name>.md         canonical role agents (edit here)
.claude-plugin/plugin.json       } Claude Code bridge to .agents/skills:
.claude-plugin/marketplace.json  } hand-written, committed, checked by
.claude/settings.json            } scripts/validate-manifests.sh
.codex/agents/<name>.toml        generated by scripts/sync.sh, committed,
                                 never edited by hand; CI fails if stale
docs/                         the hub (single source of truth)
scripts/                      sync, bootstrap, validators, work-item dispatcher
Makefile                      make verify = the same checks CI runs
```

## The adapter contract

| File | Harness | Mechanism | Last verified |
| --- | --- | --- | --- |
| `AGENTS.md` | Codex CLI, OpenCode, Copilot coding agent; Claude Code fallback | read natively | 2026-09 |
| `CLAUDE.md` | Claude Code | `@path` imports pull `docs/README.md` + the Claude guide | 2026-09 |
| `.github/copilot-instructions.md` | Copilot in VS Code | prompt prepending; defers to AGENTS.md | 2026-09 |
| `opencode.json` | OpenCode | instructions merge + named tier agents + role-agent `{file:}` prompt pointers | 2026-09 |

Rule: adapters carry no guidance. If you find yourself adding rules to an
adapter, add them to `docs/` and link instead.

## Skill pipeline

1. Canonical source: `.agents/skills/<name>/SKILL.md` (Agent Skills standard:
   `name` + `description` frontmatter, progressive disclosure), a real
   folder at the cross-tool location. Codex, Copilot, and OpenCode read it
   natively, so a fresh clone works with zero setup, and the Copilot coding
   agent sees the same skills on github.com.
2. Claude Code does not read `.agents/skills`, so a committed repo-local
   plugin points it there: `.claude-plugin/plugin.json` (`"skills":
   ["./.agents/skills"]`), `.claude-plugin/marketplace.json` (one plugin,
   `source: "./"`, `strict: true`), and `.claude/settings.json`
   (`extraKnownMarketplaces.arsenal` plus `enabledPlugins["arsenal@arsenal"]`).
   The repo settings register the plugin only after the teammate accepts the
   folder trust prompt, once per teammate per repo. The first session in a
   trusted checkout registers the marketplace in place; from the second
   session on, every session, `claude -p` included, loads the skills as
   `/arsenal:<name>`. A checkout where no session has run yet (a fresh
   machine, a CI runner, or a second clone or worktree of the same repo on
   one machine) needs `claude -p --plugin-dir .`.
   `scripts/validate-manifests.sh` checks the three files plus
   `opencode.json`; CI and `make verify` run it. Adopters must rename
   `arsenal` in the three files: Claude Code keys registered marketplaces by
   name per user, so two projects with the same name on one machine would
   share one registration.
3. `scripts/bootstrap.sh --user` links the skills into `~/.claude/skills`
   (Claude Code) and `~/.agents/skills` (Codex, Copilot CLI and VS Code,
   OpenCode, Cursor, Gemini CLI) for your other projects. The project itself
   needs no setup. Migration: links made by earlier layouts point at
   `docs/skills/` or `.claude/skills/`, some in the legacy `~/.codex/skills`
   and `~/.copilot/skills` dirs, and a dangling one makes `--user` print
   `<skill> exists and is not ours; skipping (use --force)`. Run `--remove`
   first: it sweeps `~/.claude/skills`, `~/.agents/skills`,
   `~/.codex/skills`, and `~/.copilot/skills` and deletes every link whose
   target is this repository's `docs/skills/`, `.claude/skills/`, or
   `.agents/skills/`. Or pass `--force` to replace them in place. Windows:
   run from Git Bash with Developer Mode on; the script sets
   `MSYS=winsymlinks:nativestrict`, so `ln -s` makes a real link or fails
   loudly, never a silent copy.
4. `scripts/validate-skills.sh` enforces the authoring rules (frontmatter,
   kebab-case name matching the directory, description 20 to 1024 chars,
   non-empty body). CI runs it; so does `make verify`.

Adding a skill needs no sync step. Adding a harness means nothing if it
reads `.agents/skills` natively; otherwise a committed config that points
there, the way the Claude Code plugin does. Either way, a guide in
`docs/harness/`; see the playbook there.

## Agent pipeline

1. Canonical source: `.claude/agents/<name>.md`, frontmatter limited to `name`
   and `description` (the only keys every consumer reads; `model`, `tools`,
   and `mode` are per-harness formats and live in no shared file). Claude
   Code and Copilot (CLI and VS Code) read it natively.
2. OpenCode has no agent path setting, so `opencode.json` carries one
   hand-written subagent per role: the same `description` verbatim and
   `"prompt": "{file:./.claude/agents/<name>.md}"`. The markdown is read at
   load time; nothing is copied. `scripts/sync.sh --check` fails when a
   description in `opencode.json` no longer matches the agent frontmatter.
3. Codex agents are TOML-only, so `scripts/sync.sh` builds
   `.codex/agents/<name>.toml` (TOML with `name`, `description`,
   `developer_instructions`) from the markdown; committed, never edited by
   hand, the only generated files in the repository.
4. `scripts/validate-agents.sh` enforces the authoring rules and rejects
   per-harness keys. CI and `make verify` run it.

## Script contracts

| Script | Exit 0 means | Exit 1 means |
| --- | --- | --- |
| `validate-skills.sh` | every SKILL.md conforms | at least one violation, listed |
| `validate-agents.sh` | every agent file conforms | at least one violation, listed |
| `check-links.sh` | all relative md links resolve | broken links listed as file:line |
| `validate-manifests.sh` | `OK: manifests valid`: `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.claude/settings.json`, and `opencode.json` parse; every plugin `skills` path exists; `enabledPlugins` names the marketplace's plugin as `<plugin>@<marketplace>` | one `FAIL <file>: <reason>` line per failure |
| `sync.sh` | `.codex/agents/<name>.toml` rewritten from `.claude/agents/*.md` (`--help` prints the header only) | `no frontmatter: <file>` when an agent file does not start with `---` |
| `sync.sh --check` | `OK: .codex/agents and opencode.json match .claude/agents` | `STALE .codex/agents` (with `diff -rq` on stderr) and/or `STALE opencode.json: <name> description` |
| `bootstrap.sh` | user-level wiring done with `--user` (`--remove` undoes it, legacy dirs included); a plain run only reports that the project needs no setup | `.agents/skills` missing |
| `work-item.sh` | tracker operation succeeded | backend error with remediation hint |

`work-item.sh` dispatches on `WORK_BACKEND` (`gh`, `jira`, `ado`), loads
`.env` at the repo root if present, and is the only sanctioned caller of
`gh` / Jira REST / `az boards` in the whole loop. Backends implement
`create`, `comment`, `transition`, `link`; the Jira backend speaks REST v3
with an ADF-paragraph body, the Azure backend shells to `az boards`, the
GitHub backend shells to `gh`.

## CI design

Three jobs:

- `validate` (ubuntu): bash syntax pass, skill and agent frontmatter,
  internal links, "No committed symlinks", "Generated files are in sync"
  (`scripts/sync.sh --check`), "Manifests are valid"
  (`scripts/validate-manifests.sh`), and shellcheck on every script.
- `windows` (`windows-latest`, bash): both validators, "Generated files
  are in sync" (`scripts/sync.sh --check`), and "Manifests are valid"
  (`scripts/validate-manifests.sh`), so a Windows checkout is proven, not
  assumed.
- `gitleaks`: full-history secret scan on every push and PR.

Deliberate choices:

- No runtime toolchain (no Node/Python/.NET to install): a stack-agnostic
  template must prove itself with what every runner already has. Nothing
  gets installed; `validate-manifests.sh` uses the Python 3 every runner
  already has (`python3`, or `python` on the Windows runner). See ADR-004.
- `.gitattributes` sets `* text=auto eol=lf`: Git for Windows checks out
  CRLF by default, which breaks bash scripts and makes the committed Codex
  TOML differ byte for byte from what `sync.sh --check` regenerates.
- Actions pinned by full commit SHA, per the security standard. Refresh
  deliberately: `gh api repos/<owner>/<repo>/git/ref/tags/<tag>`.
- Consumer repositories get their gate from `docs/templates/app-ci.yml`,
  which runs `make test-unit` and `make test-integration` per the testing
  standard.

## Extending

**Add a skill**: `.agents/skills/<name>/SKILL.md`, description written last
(it is the trigger); no sync step, every harness reads the folder as it is;
`make verify`; PR per the PR template.

**Add a role agent**: write `.claude/agents/<name>.md` (frontmatter: `name`
and `description` only); add the `opencode.json` entry (same `description`,
`"prompt": "{file:./.claude/agents/<name>.md}"`); `make sync` and commit the
generated `.codex/agents/<name>.toml`; `make verify`; PR. Rules and
rationale: [docs/agents/README.md](docs/agents/README.md).

**Add a tracking backend**: implement the four subcommands in
`scripts/work-item.sh` (pattern: `<backend>_<op>` functions plus dispatch),
add `.env` keys to `docs/templates/work-item.example.env`, write
`docs/integrations/<backend>.md`, update the integrations table.

**Add a harness**: entry file (prefer the existing `AGENTS.md`); a committed
config pointing at `.agents/skills` only if the tool does not read it
natively (never a copy or a symlink); a generator in `scripts/sync.sh` only
if its agent format forces one; `docs/harness/<tool>.md` answering the five
questions; matrix updates in the harness README and root README.

## Local workflow

```bash
make verify      # validate + links + generated + manifests: what CI checks
make validate    # validate-skills.sh + validate-agents.sh
make links       # check-links.sh
make generated   # sync.sh --check: Codex TOMLs and opencode.json descriptions
make manifests   # validate-manifests.sh
make sync        # regenerate .codex/agents/*.toml after editing .claude/agents/
make bootstrap   # bootstrap.sh (plain run: reports that nothing is needed)
make work-item ARGS='create "..."'   # work-item.sh
```

## Known limitations

- Harness skill paths and provider model names are the two fastest-drifting
  facts; both carry `Last verified` dates and live in single places (the
  `user_dirs` comment of `scripts/bootstrap.sh` for personal skill dirs,
  the `docs/harness/` guides plus `.claude-plugin/plugin.json` for project
  paths, `docs/models/routing.md` for models).
- The hub governs through instructions and CI; in-session enforcement beyond
  harness permissions and hooks is out of scope by design.
- `work-item.sh` Jira descriptions flatten newlines (plain ADF paragraph);
  multiline ADF would buy nothing the loop needs.
